# 本地 MVP 发布检查

[English](../en/RELEASE-CHECK.md)

这里的发布目标是：其他开发者可以获取代码、在本机初始化并运行单团队 OpenTask、按文档完成模拟交付。公网服务、生产部署与真实团队验收需要单独验证。

## 每次候选版本的检查顺序

在代码仓库根目录运行：

```sh
npm ci
npm run typecheck
npm run build
bash scripts/test-db.sh
npm run case:check
npm audit --omit=dev
npm run docs:build
```

`test-db.sh` 固定使用 `open_task_test`，包含故意制造的事务写入失败；测试日志中的 `Injected integration write failure` 属于回滚验收，最终应为 0 失败。不要把集成测试指向正常或生产数据库。案例另用 `open_task_release_case`，不清理已有案例项目。

类型检查与构建通过不代表可使用。按[案例教程](CASE-CSV-EXPORT.md)至少跟做 C 的三角色 UI 闭环；检查创建审批、清单批准、约定确认、正式进展、退回、重交、完成和刷新后的历史。能使用独立 Chrome 时也可运行原有浏览器脚本，但原有部分脚本固定连接 `4310`，会保存测试任务；先确认目标工作区。

## 通过条件

| 检查         | 通过条件                                                             |
| ------------ | -------------------------------------------------------------------- |
| 可安装       | Node 24 下 `npm ci` 成功，依赖锁文件完整                             |
| 可构建       | typecheck 与生产 build 退出 0                                        |
| 业务与事务   | 现有测试全部通过，无跳过；权限失败、数据库故障不留下部分写入         |
| 可交付       | 四任务 API 案例全部完成，13 组断言通过                               |
| 可操作       | 三角色 UI 闭环通过，刷新后保留成果与语言选择                         |
| 数据持续可用 | API/worker 重启后数据一致、停机期间队列恢复处理                      |
| 案例可恢复   | 备份恢复到新数据库，12 张表的行数及内容哈希一致                       |
| 依赖安全     | 生产依赖审计无未处理问题；网络失败应记“未验证”，不能记通过           |
| 文档可用     | Markdown 链接、截图、HTML 渲染正常，角色、按钮名称和命令匹配当前版本 |
| 可恢复       | 在发布版本或升级现有工作区前实际验证备份与独立恢复，保留证据         |

将日期、候选提交及未提交改动、命令输出、case run ID、截图与限制写入验收报告。检查失败先修复，再重跑受影响检查，不把历史报告当作当前版本结果。

## 备份、升级与恢复

正常应用数据库的既有备份工具：

```sh
bash scripts/backup.sh
bash scripts/restore-check.sh backups/<实际备份文件>.dump
```

这两个脚本的源数据库固定为 `open_task`，不会自动跟随 `DATABASE_URL`。不要用它们宣称验证了案例数据库。需要精确比较时，先暂停应用写入和 worker；两种恢复脚本共用只读校验器，比较全部 11 张应用表与 `pgboss.job`，包括时间偏好、会话和幂等记录，行数相同但内容不同也会失败。正常工作区的恢复库保留供检查；恢复脚本创建新的隔离数据库，不覆盖原库。备份包含业务数据、账号密码哈希与 pg-boss 后台任务，应作为私有运维材料，不能并入公共文档发布。提交正文与外部证据 URL 会被备份，URL 指向的远程文件不会被备份。后台任务的失败详情保留在 PostgreSQL 中。

`case:check` 最后调用 `scripts/release-case-restore.sh`，只备份模拟案例库，恢复到本次新建的临时数据库并比较 12 张表的行数和内容哈希，结束后清理该临时库与备份。运行时不要在案例库做其他写入，或启动额外 worker。案例恢复成功不替代升级现有正常工作区前对实际备份的验证。

升级已有正常工作区：停写并备份 → 保留旧代码版本 → 安装依赖 → 迁移 → 构建 → 重启 API 和 worker → 检查 `/health`、worker 心跳与一条实际任务。当前迁移为增量，但恢复流程必须实际演练；不默认以删卷或删库回退。

worker 心跳检查：

```sh
docker compose exec -T db psql -U open_task -d open_task -c "SELECT name, checked_at, error FROM worker_health;"
```

`followups` 的 `checked_at` 应持续推进，正常 sweep 每 15 秒运行，`error` 应为空。API 健康不能代替这个检查。

## 发布内容与范围

发布材料包含源代码、`package.json` 与锁文件、数据库迁移、README、`docs/` 使用文档、第三方许可及可运行的 case 脚本。HTML 可由 Markdown 重建。不要把 `artifacts/` 中的所有测试日志、会话资料或数据库备份直接当作公开发布附件。

当前代码的 `private: true` 表示不能直接 `npm publish`；本次准备的是源码或本地安装形式的发布，不变更 npm 包分发策略。版本号、正式发布渠道和上线操作仍由项目发布决定。

网络运行边界：API 与数据库均绑定 loopback；会话设计针对本机 HTTP，服务端写入还校验同源 Origin。公网 HTTPS、反向代理、跨主机访问及外部身份接入没有被本案例验证。不能只修改监听地址就把本地测试结论作为公网发布结论。

当前证据见[验收报告](RELEASE-CASE-RESULT.md)。

版本元数据与计划标签分别为 `0.1.0-alpha`、`v0.1.0-alpha`。项目采用 [Apache-2.0](../../LICENSE)，第三方声明单独保留。检查[版本说明](RELEASE-NOTES.md)及[当前候选证据](RELEASE-READINESS.md)。合并前提交必要的代码、锁文件、脚本、文档和品牌资源，在干净源码副本上执行 `npm ci` 及上述检查。合并后确保标签指向同一已验证源码树，并将发布标记为预发布。合并、推送、打标签及公开发布属于明确的发布操作。
